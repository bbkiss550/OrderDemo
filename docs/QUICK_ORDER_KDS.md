# Customer Quick Order และ KDS

อัปเดต 19 ตุลาคม 2026 ผู้ใช้ยืนยันให้เปลี่ยนสถานะได้ทั้งทีละเมนูและทั้งรอบ ใช้ภาพอ้างอิงเดิม customer 01/05/07, kitchen 11/12 และ admin 18 เป็นหลักในการจัดหน้าจอ

## การใช้งาน

1. เปิดบิลจากผังรับลูกค้าตามเดิม ลูกค้าสแกน QR ประจำบิล
2. หน้า `/order/{token}` แสดงเมนูที่เปิดขายในหมวดที่เปิดใช้งาน และมีสิทธิ์ตาม package_id ของบิล ผู้ใหญ่/เด็กในแพ็กเกจเดียวกันเห็นเมนูเดียวกัน
3. เลือกหมวด ค้นหา กด +/- และดูตะกร้าก่อนยืนยัน ส่งอาหารได้หลายรอบ ไม่คิดเงินรายจานเพิ่มจากราคาบุฟเฟต์
4. เมนูออเดอร์ของลูกค้าแสดงประวัติจากทุกเครื่องในบิลเดียวกัน พร้อมสถานะรายเมนูและรายรอบ แบ่งหน้า 20 รอบ
5. หลังบ้าน `/admin/orders` ค้นโต๊ะ เลขออเดอร์ หรือเลขบิล กรองสถานะและแบ่งหน้าได้ เปิดรายละเอียดบิลจากหน้ารับลูกค้าแล้วกด **ออเดอร์อาหาร** เพื่อดูเฉพาะบิลนั้นได้ด้วย
6. `/admin/kds` เป็นกระดาน 3 คอลัมน์ รอรับ / กำลังทำ / พร้อมเสิร์ฟ มีรายละเอียดรายการและประวัติที่เสิร์ฟแล้ว
7. กด **พิมพ์ใบสั่งอาหาร** บนการ์ด KDS หรือรายละเอียดออเดอร์เพื่อเปิดหน้าพิมพ์แยกรอบ แล้วกดพิมพ์เพื่อเลือกเครื่องพิมพ์ ใช้ความกว้างและระยะขอบตามค่าร้าน เช่น 58/80 มม. มีตัวเลือก **พิมพ์ซ้ำเป็นสำเนา** โดยผู้ใช้เลือกเอง ไม่ถือว่าการเปิดหน้าพิมพ์เท่ากับพิมพ์กระดาษสำเร็จ

## สถานะและสิทธิ์

`PENDING → COOKING → READY → SERVED` เปลี่ยนข้ามขั้นหรือย้อนกลับไม่ได้ รองรับทั้งรายเมนูและทั้งรอบ รายเมนูหมายถึงจำนวนทั้งหมดของเมนูนั้นในรอบ ยังไม่แยกเสิร์ฟบางจานจากรายการเดียวกัน

สถานะของรอบอิงขั้นที่ยังค้างน้อยที่สุด เช่น มี 1 เมนูพร้อมเสิร์ฟและอีกเมนูรอรับ รอบยังเป็นรอรับ ปุ่มรวมเปลี่ยนเฉพาะรายการที่อยู่ขั้นเดียวกับรอบ ไม่ลดขั้นรายการที่ทำไปแล้ว รายการพร้อมเสิร์ฟสามารถยืนยันเสิร์ฟแยกได้แม้รายการอื่นยังรออยู่

- ADMIN: ดูและเปลี่ยนสถานะได้ทั้งหมด
- KITCHEN: เข้าระบบแล้วไป KDS; เปิด–ปิดอาหารยังอยู่ที่ `/admin/kitchen` ดูและเปลี่ยนสถานะอาหารได้ ไม่มีสิทธิ์การเงิน/ตั้งค่าร้าน
- CASHIER: ดูออเดอร์และยืนยันเสิร์ฟเฉพาะอาหาร READY ได้ API ปฏิเสธการเริ่มทำ/ทำให้พร้อมเสิร์ฟและการเข้าหน้า KDS

เมื่อย้ายบิล ทุกหน้าดึงชื่อโต๊ะปัจจุบันจาก bills และยังเก็บชื่อโต๊ะตอนสั่งไว้ในรอบ บิลที่ปิดแต่ยังมีอาหารค้างแสดงคำเตือนในครัว ไม่ซ่อนออเดอร์นั้นและไม่ยกเลิกอัตโนมัติ

## ข้อมูลและความถูกต้อง

- รัน `sql/006_food_orders.sql` ด้วยตนเองหลัง 001–005 เพิ่ม order_rounds และ order_items ไม่แก้บิล/ราคา/เมนูเดิม ไม่มี schema update ตอน start
- บิลคือ session หลัก ใช้ QR เดิมเมื่อสั่งเพิ่ม เปิดบิลใหม่จึงได้ QR ใหม่
- บิลบันทึก package_id ไว้แล้ว การปิด master package หยุดเปิดบิลใหม่ แต่ไม่ตัดสิทธิ์บิลที่เปิดอยู่ การแก้ menu/category/package switch มีผลกับรายการใหม่ทุกครั้ง
- ตรวจ token สถานะบิล เวลา category/menu active และสิทธิ์แพ็กเกจจากฐานข้อมูลก่อนสร้างรอบ ไม่เชื่อชื่ออาหาร ราคา หรือสิทธิ์จาก client
- จำกัดเชิงเทคนิค 1–50 เมนูต่อรอบ จำนวน 1–99 ต่อเมนู รายการซ้ำไม่ผ่าน validation
- ล็อกแถวบิลเพื่อเรียงหมายเลขรอบ รองรับส่งจากหลายเครื่องพร้อมกัน และใช้ lock เดียวกับ checkout การปิดบิล/หมดเวลาหยุดออเดอร์ใหม่
- ตรวจเวลาจริงด้วย clock_timestamp หลังล็อกเมนูด้วย ป้องกันคำขอที่รอ lock จนหมดเวลาแล้วผ่านเพราะอิงเวลาเริ่ม transaction
- ล็อกสิทธิ์อาหารขณะรับออเดอร์ สร้างรอบกับรายการทั้งหมดใน transaction เดียว เก็บ snapshot ชื่อ/หมวด/emoji/จำนวน เพื่อคงประวัติเมื่อ master ถูกแก้
- ทุกการส่งมี UUID และ hash รายการที่เรียงแน่นอน unique ต่อบิล คำขอเดิมและ payload เดิมคืนรอบเดิม แม้บิลเพิ่งหมดเวลาหรือปิดแล้ว เพื่อยืนยันผลที่เคยรับสำเร็จ การใช้ key เดิมกับรายการต่างกันเป็น 409
- ตะกร้าอยู่ในหน่วยความจำ frontend เก็บเฉพาะคำขอที่ยังไม่ทราบผลใน sessionStorage เพื่อ retry ข้าม reload ด้วย key เดิม ไม่ใช้ storage เป็นข้อมูลออเดอร์จริง ประวัติอ่านจากเซิร์ฟเวอร์ทั้งหมด
- การเปลี่ยนสถานะล็อกรอบและตรวจ version ครัว 2 จอที่กด version เดียวกันจะสำเร็จจอเดียว อีกจอรับ 409 และโหลดข้อมูลล่าสุด
- ใช้ session/CSRF เดิม POST ของลูกค้ายังต้องมี CSRF จากหน้า QR; token ของบิลไม่เปิดให้เรียก admin API
- Audit บันทึก ORDER_CREATE ในนามลูกค้า QR และ ORDER_STATUS ในนามบัญชีพนักงาน ไม่มี QR token หรือรหัสผ่านใน audit

## การอัปเดตหน้าจอ

ลูกค้า KDS และหน้าออเดอร์หลังบ้าน polling ทุก 3 วินาที เฉพาะขณะหน้าแสดงอยู่ เมื่อกลับมาเปิดหรือเครือข่ายกลับมาจะดึง snapshot ล่าสุด มีสถานะการเชื่อมต่อและปุ่มอัปเดตในหลังบ้าน ไม่มี WebSocket/SSE ในรุ่นนี้

โทรศัพท์จริงต้องเข้าถึง URL ใน QR ได้ ค่า Docker ปัจจุบันยัง bind เฉพาะ localhost ตามเดิม การทดสอบ LAN ต้องตั้ง APP_BIND / URL ร้าน และตรวจเครือข่ายตาม README

## API

| Method | Endpoint | หน้าที่ |
| --- | --- | --- |
| GET | `/order/{token}/state?page=0` | บิลที่อนุญาตให้แสดง เมนู และประวัติรอบของบิลนั้น |
| POST | `/order/{token}/rounds` | `{requestKey,items:[{menuId,quantity}]}` |
| GET | `/api/admin/orders` | `status,q,billId,page,size` ขนาดหน้า 20/50/100 |
| GET | `/api/admin/orders/{id}` | รายละเอียดรอบและสถานะรายเมนู |
| GET | `/admin/orders/{id}/print` | หน้าพิมพ์ใบสั่งอาหารจาก snapshot รายการ โต๊ะปัจจุบัน และเวลาสั่ง ไม่มีราคา/QR; ADMIN/CASHIER/KITCHEN เข้าถึงได้ |
| POST | `/api/admin/orders/{id}/status` | `{status,version,itemId?}` ไม่ระบุ itemId คือเปลี่ยนทั้งขั้นของรอบ |

## การตรวจสอบและขอบเขต

`OrderServiceTest` เพิ่ม 2 unit tests สำหรับ fingerprint/validation รวมชุด Java 15 รายการผ่าน `scripts/order-smoke.cjs` ใช้ API และฐานข้อมูลจริง สร้างและล้างเฉพาะข้อมูล QA ของรอบทดสอบ รวมการส่งหลายเครื่อง/กดซ้ำ, CSRF/role, เมนูปิด/หมวดปิด/สิทธิ์แพ็กเกจ, snapshot, ย้ายโต๊ะ, หมดเวลา/checkout, สถานะทีละเมนู/ทั้งรอบ, version ชน, แบ่งหน้า, QR บิลใหม่ และ audit

สคริปต์ยังจำลอง DOM ด้วย jsdom โดยโหลด HTML/scripts/assets และเรียก API ที่ให้บริการจริง ทดสอบหน้าเลือกอาหาร ตะกร้า lost-response แล้ว reload/retry ด้วย key เดิม หน้า KDS/ออเดอร์ รายละเอียด และปุ่มสถานะ ตรวจการ escape ชื่ออาหาร

ยังไม่ได้ตรวจภาพบน iPad จริง การสแกน QR บน LAN เครื่องพิมพ์ครัว หรือทดสอบโหลดระยะยาว ไม่มีการเพิ่มเรียกพนักงาน ยกเลิก/ย้อนสถานะ อาหารเพิ่มเงิน หรือ payment gateway ในรอบนี้
